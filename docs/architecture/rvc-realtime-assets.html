RVC 实时推理模块声明

范围：只讲 mozart-rvc 进程内部的实时推理。麦克风、pre 的 DSP、播放路由只作为输入输出边界，不展开。每站先列模块事实和参数，再用“补充解释”说明参数在链路里改什么。文件链见 rvc-module.html；系统运行时全貌见 rvc-realtime-module.html。

下文先用全称定义，之后一律复用同一名称。

契约帧：音频进程和推理进程之间传输的固定长度帧。输入 16 kHz、320 个采样点、20 ms；输出 48 kHz、960 个采样点、20 ms。

块：推理进程内部一次处理的新音频长度。实时链是 240 ms，等于 3840 个 16 kHz 采样点。

分析窗：推理进程每次实际喂给内容特征网络的音频长度。实时链是 2.8 秒，等于 44800 个 16 kHz 采样点。

生成器前段：代码名 front。它把内容特征、音高、说话人编号和潜噪声变成潜变量 z。

生成器解码段：代码名 decoder。它把潜变量 z 变成波形。

共享引擎：所有模型共用的一份引擎。本文里指内容特征网络 HuBERT 和音高提取网络 RMVPE。

音高编号：生成器认识的离散音高，记作 pitch，取值 1 到 255。连续音高记作 pitchf，单位 Hz。

可选索引：代码名 index。它是训练集音色向量的库，按模型独立，不导出成引擎。

参数来源分五种，每个参数后注明：〔生成时固定〕在导出 ONNX 时填，之后不改；〔编译时固定〕在 ONNX 编译成 engine 时定；〔推理时可调〕在启动流或写配置时能改；〔模型决定〕来自 pth 或模型配置；〔代码写死〕是代码常量，改它等于改实时契约。

补充解释：参数标记怎么读

  • 〔生成时固定〕：这个值在导出 ONNX 时写进计算图。改了要重新导出，还要重新编译引擎。实时链的帧数大多属于这一类。
  • 〔编译时固定〕：这个值在 TensorRT 编译时写进 engine。改了只需要重新编译，但编译必须在目标设备上做。
  • 〔推理时可调〕：这个值在启动流或写配置时注入，不需要重新导出或编译。实时链能调的会话参数很少，只有五个。
  • 〔模型决定〕：这个值来自 pth 或模型目录里的 config.json。换模型可能变，但用户不直接填。
  • 〔代码写死〕：这个值是 C++ 常量。配置改不了，换模型也不变。少数值由引擎导出固定，换引擎仍可能变。

先认识几个词

张量形状
用一串数字描述一次输入或输出有多少维、每维多长。比如 [1, 280, 768] 表示 1 条样本、280 帧、每帧 768 个数。
帧与帧移
处理声音时不会一次看完整段，而是切成很短的片段，每一段叫一帧。帧移是相邻两帧起点相距多少个采样点，决定“隔多久看一次”。
潜变量
生成器中间的一层数字，记作 z。它已经把内容、音高和音色揉在一起，但还不是波形。front 输出它，decoder 吃它。
TensorRT
NVIDIA 的推理编译器。它把 ONNX 计算图针对具体显卡编译成 engine，换来更低的推理延迟。engine 绑定设备和 TensorRT 版本。
定长与动态
定长表示每次输入的形状固定，编译时就能完全优化；动态表示某些维度可以变，运行时才确定。实时链用定长。
采样率
每秒钟给声音“拍照”的次数，单位 Hz。实时链输入固定 16000 Hz，输出固定 48000 Hz。
音高
声音听起来的高低，单位 Hz。生成器不直接吃连续频率，而是吃量化后的音高编号。

输入输出边界

上游是 pre 音频进程。它把麦克风采集、降噪、整形和降采样处理成 16 kHz 契约帧，再通过 Unix 数据报发给 mozart-rvc。

下游仍是 pre。mozart-rvc 把 48 kHz 输出帧发回去，pre 按路由决定播放直出声音还是变声后的声音。

pre 的 16 kHz 帧 → mozart-rvc 实时推理 → 48 kHz 帧 → pre 播放

pre 的 DSP 细节不在本文范围。本文从“16 kHz 契约帧进入 mozart-rvc”开始，到“48 kHz 契约帧离开 mozart-rvc”结束。

补充解释

  • 为什么把边界放在 pre：RVC 推理只关心 16 kHz 音频帧和元数据。麦克风、降噪和播放属于音频进程，混进来会把问题拆散。
  • 输入帧里有什么：16 字节元数据加 320 个 float32 样本。元数据包含时间戳、帧号、VAD 标记、能量、置信度和分段号。
  • 输出帧里有什么：同样的元数据加 960 个 float32 样本。推理进程每收到一帧输入就回一帧输出，输出不足补零。

总流程

16 kHz 契约帧 → 帧调度 → HuBERT 与 RMVPE → 音高映射 → 索引检索（可选）→ front → decoder → SOLA → 48 kHz 契约帧

真实推理不是一帧一帧独立做，而是先攒成 240 ms 的块，再带上 2.5 秒过去上下文，凑成 2.8 秒分析窗。分析窗里只有最新一块会被回放，历史只用来提供上下文。

HuBERT 和 RMVPE 可以并行跑。前者回答“说了什么”，后者回答“音高是多少”。两者结果在 front 汇合，再交给 decoder 合成波形。

补充解释：整条推理在做什么

  • 一句话概括：把新来的一小段声音放进 2.8 秒上下文里，提取内容和音高，换成目标音色的潜变量，再合成 240 ms 新声音。
  • 为什么不能只喂 240 ms：RVC 的生成器需要看到足够长的历史，才能保持音色、相位和韵律连续。2.5 秒过去上下文是实时链的折中。
  • 为什么输出只有 240 ms：decoder 实际生成 300 ms，其中 60 ms 用来和上一块做对齐和淡化，真正推进的是 240 ms。

第 1 站 帧调度与窗口

这一站决定什么时候推理、拿多长的音频推理、结果怎么排回 20 ms 帧节拍。它不产出引擎。

块长，3840 个 16 kHz 采样点〔代码写死〕。它等于 240 ms。每攒够一块新音频，才触发一次推理。

过去上下文，40000 个 16 kHz 采样点〔代码写死〕。它等于 2.5 秒。每块重读这段历史，给生成器提供上下文。

分析窗，44800 个 16 kHz 采样点〔代码写死〕。它等于 2.8 秒，由过去上下文、当前块和 960 个采样点的对齐余量组成。HuBERT 和 RMVPE 都吃这个窗。

启动缓冲，400 ms〔代码写死〕。首次出声前先等这么久，再等输出环攒满一个完整块。它用来吸收推理耗时和送达抖动。

输出环，16 秒〔代码写死〕。推理可以领先消费端数块。环满丢最旧并计数。

帧调度接口

  • 输入参数：没有用户参数。块长、过去上下文、启动缓冲、输出环都由代码固定。
  • 输入信号：16 kHz 输入帧，每帧 320 个 float32 样本；元数据包含 pts_ns、frame_idx、vad_flag、energy_db、conf、segment_id。
  • 输出：48 kHz 输出帧，每帧 960 个 float32 样本。每收到一帧输入就回一帧输出，输出环不足时补零。
  • 内部中间量：分析窗 [44800]；单块 decoder 输出 [14400]；实际推进 [11520]；淡化尾 [2400]。

补充解释

  • 为什么块长是 240 ms：块越长，上下文越足、推理次数越少，但延迟越高。240 ms 是实时链在延迟和连续性之间的折中。
  • 为什么过去上下文是 2.5 秒：生成器需要历史来维持音色和韵律。2.5 秒是当前实测可用值，不是理论下限。
  • 为什么分析窗是 2.8 秒：2.5 秒历史加 240 ms 当前块，再加 60 ms 对齐余量，正好 2.8 秒。
  • 为什么 1:1 回帧：输入和输出都是 20 ms 一帧。推理快慢由输出环吸收，接口始终保持一帧进、一帧出。
  • 静音和断流怎么处理：整窗没有 VAD 标记就跳过推理，输出等长静音；帧号缺口过大或时间戳跳变就清环、丢淡化尾、恢复启动缓冲。

第 2 站 内容特征 HuBERT

HuBERT 从 16 kHz 声音里提取“说了什么”的内容特征。它不负责音色，也不负责音高。

HuBERT 接口

  • 生成时参数：--hubert-path 指共享 HuBERT 模型目录；--output 指定 ONNX 文件名；--samples 固定 44800；--opset 默认 17；--dynamic 在实时链必须关闭。
  • 编译时参数：--hubert 指定 ONNX；--fp16 可选；--trtexec 可指定编译器路径。
  • 推理时参数：realtime_hubert_path 指向共享引擎，留空时按约定文件名自动发现。没有用户可调的会话参数。
  • 输入信号：audio float32 [1, 44800]，16 kHz 下的 2.8 秒 PCM。
  • 输出：features float32 [1, 139, 768]。运行时把每帧复制一份，凑成 [280, 768] 再送 front。

补充解释

  • 为什么输入固定 44800：实时链每个分析窗正好 2.8 秒，16 kHz 下就是 44800 个点。固定输入让 TensorRT 可以完全优化。
  • 为什么输出 139 帧：HuBERT 的卷积栈每 320 个采样点出一帧，44800 个点出 139 帧。
  • 为什么要变成 280 帧：生成器每秒要 100 帧，HuBERT 每秒只有约 50 帧。把每帧复制一份，正好补齐到 280 帧。
  • 为什么所有模型共用一份：HuBERT 学的是通用语音内容，不包含某个音色的特征。换音色不需要换它。
  • 为什么实时链必须是 TensorRT：启动时会校验引擎必须是健康的 TensorRT、输入正好 [1, 44800]、输出有限。ONNX 兜底不满足实时延迟。

第 3 站 音高提取 RMVPE

RMVPE 从声音的频谱里提取音高曲线。它不负责内容，也不负责音色。

mel 前端接口

  • 输入参数：没有用户参数。128 个 mel 频带、1024 点 FFT、160 点帧移、30 到 8000 Hz 都写死。
  • 输入信号：audio float32 [4960]，从 44800 分析窗末尾截取。
  • 输出：mel float32 [1, 128, 32]。

RMVPE 接口

  • 生成时参数：--rmvpe-path 指 RMVPE 权重文件；--rvc-source 指上游 RVC 源码；--output 指定 ONNX 文件名；--frames 固定 32；--opset 默认 17；--device 默认 CPU。
  • 编译时参数：--rmvpe 指定 ONNX；--fp16 可选；--trtexec 可指定编译器路径。
  • 推理时参数：f0_method 只接受 rmvpe；realtime_rmvpe_path 指向共享引擎。mel 前端参数不开放。
  • 输入信号：mel float32 [1, 128, 32]。
  • 输出：f0 float32 [1, 32, 360]，是显著性谱，不是 Hz。运行时解码成 32 个 F0 值，更新 1024 帧音高缓存。

补充解释

  • 为什么只看 4960 个采样点：音高只需要当前块附近。4960 个点刚好凑出 32 帧 mel，覆盖当前块和少量重叠上下文。
  • 为什么每块重算 4 帧重叠：固定形状的 RMVPE 在窗边缘不可靠。每块丢掉 3 个左缘帧和 1 个右缘帧，把 28 个新帧写入缓存。
  • 为什么音高缓存是 1024 帧：front 需要 280 帧音高，其中 250 帧来自历史。1024 帧足够覆盖历史，又不会占太多内存。
  • 为什么只支持 rmvpe：代码里只实现了 rmvpe。其他方法名会直接报错，不会静默返回全零音高。
  • 为什么所有模型共用一份：RMVPE 学的是通用音高提取，不包含音色。换音色不需要换它。

第 4 站 音高映射

这一站把连续音高曲线换成生成器认识的离散编号，同时应用变调。

音高映射接口

  • 输入参数：pitch_shift 推理时可调，范围 -12 到 12，单位是半音；f0_method 只接受 rmvpe。
  • 输入信号：RMVPE 缓存里的 F0 值。当前块更新 28 帧，接口按 280 帧读取。
  • 输出：pitch [1, 280]，1 到 255 的离散编号；pitchf [1, 280]，变调后的连续频率。front 用完整的 pitch，decoder 用最后 30 帧 pitchf。

补充解释

  • 变调半音数怎么改声音：每加 1 个半音，频率乘以 2 的 1/12 次方。加 12 个半音升高一个八度，减 12 个半音降低一个八度。
  • 为什么要量化成 1 到 255：生成器不吃连续频率，只认离散编号。按 mel 刻度分档，低音区更密、高音区更疏，更符合人耳感觉。
  • 为什么 front 和 decoder 拿的音高不一样：front 需要 280 帧离散编号来对齐内容特征；decoder 只需要最后 30 帧连续频率来合成新块波形。

第 5 站 索引检索

这一站是可选的。它用训练集特征库修正内容特征，让音色更接近训练数据。没有 index 文件时不执行。

索引接口

  • 输入参数：index_rate 推理时可调，范围 0 到 1；候选表数 1 和近邻数 8 写死；index 文件按模型独立。
  • 输入信号：HuBERT 特征的尾部。当前 280/250 几何下是 [14, 768]，前面 125 帧属于过去上下文，不参与检索。
  • 输出：同形状的混合特征 [14, 768]。没有 index 文件或 index_rate=0 时原样返回。

补充解释

  • 检索在做什么：在训练集特征库里找最相似的 8 个样本，按距离平方反比加权，再把它们的音色特征混进当前特征。
  • index_rate 改什么：0 表示完全不用检索，1 表示完全用检索特征。中间值在模型自己的音色和训练集音色之间过渡。
  • 为什么只查尾部：过去上下文只用来提供历史，不需要检索训练集音色。只查新音频对应的特征，既省时间，也避免把历史音色反复混进来。
  • 为什么不能跨模型共用：index 的向量和音色、训练集绑定。换模型通常要同时换 index。

第 6 站 生成器 front

front 把内容特征、音高、说话人编号和潜噪声变成潜变量 z。它包含目标音色的权重，必须和 decoder 成对使用。

front 接口

  • 生成时参数：--front-output 指定 ONNX 输出；--front-frames 固定 280；--skip-head 固定 250；--return-frames 固定 30；--decoder-frames 固定 30；--opset 默认 18；--dynamo-front 可选；--test-data-dir 可选；--rvc-source 必填。
  • 编译时参数：--front 指定 ONNX；--fp16 可选；--trtexec 可指定编译器路径。
  • 输入信号：feats float32 [1, 280, 768]；p_len [1]，值 280；pitch [1, 280]，值 1 到 255；sid [1]，说话人编号；latent_noise float32 [1, 192, 54]。
  • 输出：z float32 [1, 192, 30]，取 280 帧潜变量中的最后 30 帧。

192 是潜变量通道数，由 pth 决定，常见值是 192。54 由 280、250 和 24 推出。

补充解释

  • 为什么 front 看 280 帧、只返回 30 帧：front 需要 250 帧历史才能把新音频的特征放到正确上下文里，但输出只需要覆盖新块。
  • 为什么 latent_noise 是 54 帧：front 先算了 280 帧，前 226 帧属于丢弃的历史部分，剩下 54 帧里再取最后 30 帧返回。
  • 潜噪声改什么：它给合成过程提供细微纹理和气息。运行时用固定种子 114514 生成，跨块连续，不是用户参数。
  • 为什么不能跨模型共用：front 里带的是目标音色权重。不同 pth 必须各自导出，而且不能拿 A 的 front 配 B 的 decoder。

第 7 站 生成器 decoder

decoder 把 z、连续音高、说话人编号、源相位和源噪声合成波形。

decoder 接口

  • 生成时参数：--decoder-output 指定 ONNX 输出；--decoder-frames 固定 30；--return-frames 固定 30；--skip-head 固定 250；--opset 默认 18；--rvc-source 必填。
  • 编译时参数：--decoder 指定 ONNX；--fp16 可选；--trtexec 可指定编译器路径。
  • 输入信号：z float32 [1, 192, 30]；pitchf float32 [1, 30]；sid [1]；source_phase float32 [1, 1, 1]；source_noise float32 [1, 14400, 1]。
  • 输出：audio float32 [1, 1, 14400]，48 kHz 下的 300 毫秒。40 kHz 模型输出 [1, 1, 12000]。

source_phase 和 source_noise 的最后一维是源维度，由 pth 决定。40 kHz 模型的 source_noise 是 [1, 12000, 1]。

补充解释

  • 为什么输出 300 ms、实际只推进 240 ms：多出来的 60 ms 用来和上一块做 SOLA 对齐和淡化，避免接缝咔哒声。
  • 源噪声和源相位改什么：它们决定合成波形的相位和气息细节。运行时内部随机生成，不是用户参数。
  • 为什么 decoder 帧数必须等于返回帧数：front 返回多少帧 z，decoder 就必须吃多少帧。脚本在导出时强制检查。
  • 为什么 40 kHz 模型不能直接用：decoder 输出长度按采样率算。48 kHz 下 30 帧是 14400 样本，40 kHz 下是 12000 样本，运行时也会拒绝实时流。

第 8 站 SOLA 与输出

这一站把 decoder 每块独立生成的波形对齐并拼成连续音频。

SOLA 接口

  • 输入参数：没有用户参数。SOLA 搜索 480 个采样点、淡化 2400 个采样点、每块推进 11520 个采样点都写死。
  • 输入信号：decoder 输出的单块音频 [14400]，48 kHz。
  • 输出：每块 11520 个输出样本，等于 240 毫秒。前 2400 个样本与上一块淡化尾对齐，再取紧随其后的 2400 个样本作为下一块的淡化尾。
  • 内部输出环：16 秒容量。播放侧每 20 ms 取 960 个样本，不够时补零。

补充解释

  • 为什么要 SOLA：decoder 每块独立生成，块边界可能有相位差。先在 480 个样本内找最对齐的位置，再淡化，接缝才不容易听到咔哒声。
  • 为什么淡化是 2400 个样本：2400 个样本等于 50 ms，足够盖住块边界，又不会把两块的声音混得太久。
  • 为什么输出环要 16 秒：推理偶尔会比播放快。输出环让推理领先几块，播放侧仍然按 20 ms 节拍稳定取帧。

参数在推理里改什么

pitch_shift
改音高，单位半音，-12 到 12。它进入音高映射，改变 front 的离散音高和 decoder 的连续音高。正数升调，负数降调。
index_rate
改音色检索强度，0 到 1。0 完全不用训练集特征，1 完全用检索特征。没有 index 文件时不起作用。
protect
辅音保护比，0 到 0.5。实时链接受这个参数，但当前不执行保护混合，所以传了也不改变输出。
rms_mix_rate
音量包络混合比，0 到 1。实时链接受这个参数，但当前不做音量包络校正，所以传了也不改变输出。
f0_method
音高提取方法。当前只接受 rmvpe，换别的值直接报错。
block / past / startup
块长、过去上下文和启动缓冲。它们决定延迟和连续性，写死在代码里。改它们等于改实时契约，不能只改一个值。
fp16
编译时精度开关。开启后 engine 更小更快，可能有轻微数值差异。它不改变接口，只改变 engine 的数值和性能。
sample_rate
模型原生采样率。实时链要求它等于输出采样率 48000 Hz。40 kHz 模型会被能力门控拒绝。
index / nprobe / neighbours
检索库、候选表数和近邻数。index 按模型独立；候选表数 1 和近邻数 8 写死，改它们会改变检索范围和音色混合结果。

补充解释：为什么只有这几个真正可调

  • 会话参数只有五个：pitch_shift、index_rate、rms_mix_rate、protect、f0_method。它们在 StartStream 时固定，避免运行中改参数造成块边界状态不一致。
  • 为什么 protect 和 rms_mix_rate 不生效：实时路径优先低延迟，没有做辅音保护和音量包络校正。参数仍然接受并校验范围，是为了保持控制面统一，将来补实现时不用改接口。
  • 为什么块长这些不开放：改块长会牵动窗口、淡化、SOLA、启动缓冲和帧契约。单改一个值无法保持连续，所以它们被设计成代码常量。
  • 为什么 fp16 是编译时开关：TensorRT 在编译时决定数值精度。运行时改配置不会改变已经编好的 engine。

引擎从哪来

实时推理用四个引擎：每个模型的 front、decoder，以及所有模型共享的 HuBERT、RMVPE。

front 和 decoder 从目标音色的 pth 导出，包含音色权重，不能跨模型共用；同一 pth 的 front 和 decoder 必须成对使用。

HuBERT 和 RMVPE 从共享模型导出，不包含音色权重，可以跨所有 v2 模型共用。换音色只换 front 和 decoder。

index 是可选的训练产物，按模型独立。没有它也能推理，只是不能用 index_rate 做检索混合。

引擎在目标设备上编译，绑定设备和 TensorRT 版本。同名 .engine 优先于 .onnx；实时 HuBERT 和 RMVPE 必须使用健康的 TensorRT 引擎。

和文件链的差异

文件链从 pth 导出一个动态生成器；实时链导出 front 和 decoder 两个定长引擎。

文件链的形状可以用档位调；实时链的形状由音频代码锁死，不能通过编译参数改。

文件链有辅音保护、音量包络和后处理；实时链目前不应用 protect 和 rms_mix_rate。

文件链可以处理 40 kHz 模型；实时链只接受与输出采样率一致的 48 kHz 模型。

适用范围

本文依据当前代码和文档说明 RVC 实时推理的模块接口，不是实测报告。性能、延迟和音质数据见 reports/ 下的对应报告。

未验证项：

  • --fp16 对实时音质和延迟的影响，未在本文范围实测。启用前应按目标模型做对比。
  • 40 kHz 模型的实时链路未实现。阻塞原因：帧契约与输出缓冲按 48 kHz 设计。解除条件：完成实时原生多采样率改造并板端验证。
  • front 和 decoder 回退 ONNX 的实时延迟未测量。阻塞原因：实时链通常使用 TensorRT 引擎。解除条件：在目标设备上对比 ONNX 与 engine 的推理耗时。
  • 实时流中换模型的块边界状态语义未完全验证。阻塞原因：过去上下文、SOLA 状态和音高缓存在换模型时的归属规则尚未定稿。
