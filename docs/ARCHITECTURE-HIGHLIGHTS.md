# 架构亮点：维护性、开发流程与 DevOps

本文面向评审和后来接手的人，说明 Mozart 仓库在长期维护上的做法。`REQUIREMENTS.md` 里没有单独一项叫“维护性”，相关内容主要落在“架构设计合理性”和“功能扩展潜力”里，“技术通用价值”和“系统稳定性”也沾边。下面按几个方面整理，尽量说得直白一些。

简单说，这个仓库的维护性靠三件事：同一个东西只定义一次，每个模块只管自己的事，每个决定和每次实测都留下记录。开发过程按规格先行、计划确认、小步提交来做；DevOps 部分则把构建、检查、部署和测试收进了少数几个固定入口。

## 1 同一个东西只定义一次

### 1.1 跨语言帧契约

进程之间传的音频帧，定义只写在 `core/include/mozart/frame.h` 这一个 C 头文件里。Rust 那边不另写一套，而是照着头文件做一个 `#[repr(C)]` 的镜像，再加编译期断言。大小对不上，编译就过不去。

两边的测试还读同一组二进制夹具，逐字节比对。这样一来，“一帧到底多少采样点、多少个字节”这类问题，不太容易出现两套说法。改契约的时候，也只需要改一处，剩下的交给编译器提醒。

### 1.2 配置 schema

配置的段、键、类型、默认值和范围，只在 `docs/config.md` 写一份。代码里的解析器要跟它对齐。控制模块的规格讲“配置怎么用”，但不重复抄一遍 schema。这样文档和代码之间只有一个对齐点。

### 1.3 文档各管一段

模块规格里定了分工：接口契约写在提供方模块的规格里，模块行为写在模块自己的文件里，只有跨模块的事情才放到总索引。每个细节只写一处，别的地方链接过去。

设备目录、资产和部署步骤这类信息，README 直接标了 `docs/SETUP.md` 是唯一权威。这样改部署流程时，不用满仓库找还有哪份文档写着旧路径。

## 2 模块边界清楚，扩展点尽量做成配置

### 2.1 依赖方向

core 是最底层的公共契约和传输库，不依赖别的组件。pre、daemon、rvc 都只依赖 core。

daemon 负责生命周期和控制命令，但不碰音频数据路径。它通过进程间通信指挥 pre 和 rvc，不产生链接依赖。这样控制面出问题，不至于直接把音频链路拖垮。

推理单独放在一个 C++ 进程里。它崩了，采集和播放不会一起消失。推理这层也能独立替换实现，比如换 ONNX Runtime 或 TensorRT，不需要动 Rust 运行时。

### 2.2 扩展点

往系统里加东西，多数时候有现成位置。

pre 的消费者是一个列表，想多接一路处理，就加一项配置。模型是一张注册表，加模型也是改配置。实时变声和文件转换共用同一套帧契约和推理进程，只是调度方式不同。

配置还分成“运行时生效”和“重启生效”两类。`config set` 碰到需要重启的键，会明确返回 `restart_required` 和受影响的模块，不会假装已经生效。这个小约定，能省掉不少“为什么改了没反应”的排查时间。

## 3 决定和证据留得住

### 3.1 变更记录

模块规格索引里有一份按日期写的变更记录。每个决定当时怎么定的、取代了哪一版，都能翻到。跨模块的冲突单独列出来，标清楚是已定、待定，还是已定但还没实现。

### 3.2 规格与代码对齐

模块规格从 2026-11-15 起改成了待办清单。做了的打勾，没做的附上文件和行号，动手前可以先复核。这样文档不容易悄悄和代码脱节。

### 3.3 实测报告

实测记录按主题和日期放在 `reports/` 下。每份报告开头写配置和测量方法，文末有“适用范围”，交代配置、样本数和未验证的部分。

验收原则里还专门说，完成率要拿全部输入当分母，不能只算成功的那些。性能数字要写清设备、模型、计时起止点和统计范围。未验证项要写阻塞原因和解除条件，不能拿“尚未验证”当挡箭牌。

## 4 开发流程：规格先行、计划确认、小步提交

这一节讲代码是怎么一步步写出来的。它和维护性有关，因为流程本身也在决定仓库以后好不好改。

### 4.1 规格先行（Spec-Driven Development，SDD）

这个项目基本按“先写规格，再写代码”的方式推进。每个模块在 `docs/SPEC/` 下有一份规格，比如 core、pre、rvc、daemon 和语言链路。接口契约写在提供方模块的规格里，模块行为写在模块自己的文件里。动手之前先看规格，代码写完再回头更新规格。

规格不是写完就放着。现在每份规格都是一张待办清单，做了的打勾，没做的附上文件和行号。动手前先复核这些证据，避免照着过期文档写代码。跨模块的分歧集中放在总索引里，标清楚是已定、待定，还是已定但还没实现。

这样做的好处是，讨论的结论有地方落，不会只留在聊天记录里。后来的人也能从规格里看到“为什么这样做”，而不只是“现在是这样”。

### 4.2 计划模式（Plan Mode）

对不算小的改动，先在计划模式里探索一遍。把要改的文件、可能的方案和验收方式列出来，确认之后再写代码。

讨论的时候一次只聊一个点，确认了再进下一个。这个习惯写在规格索引里，不是临时起意。计划阶段发现的问题，也会顺手记到规格或变更记录里，避免下次再讨论一遍。

### 4.3 原子级更改

代码按模块小步推进，每一步独立验收。提交也尽量做到一个提交只做一件事，提交说明写清楚做了什么，不写“修复 bug”这种空话。

检查脚本会根据改动路径只跑相关阶段。只改 Rust 就不跑 C++，只改文档就只跑文档检查。这样小步提交不会因为全量检查太慢而被绕过去。

小步的好处比较实际：review 的范围小，出问题时容易定位，回滚也不用牵一大片。

## 5 DevOps 技术栈的落地

这一节讲具体用了哪些工具，以及它们怎么接在一起。

### 5.1 构建：两套工具链，一个仓库

运行时用 Rust，构建靠 Cargo workspace。推理层用 C++，构建靠 CMake、Ninja 和 CTest。两边在同一个仓库里，按目录划分。

CMake 用 `CMakePresets.json` 管理构建配置。主机上有调试、地址检查（ASan/UBSan）和线程检查（TSan）几个预设；设备上用 release 预设，打开 TensorRT/ONNX Runtime 和 ARM 优化。拿到仓库的人不用自己拼编译参数，按预设名构建就行。

纯 Rust 组件不放 `CMakeLists.txt`；CMake 根按目录是否存在自动纳入。这样加一个 Rust 组件，不会多出一份需要手动维护的构建配置。

### 5.2 检查与 CI：一条命令，本地和 CI 共用

检查命令只在 `tools/ci-local.sh` 定义一次。它分五个阶段：仓库卫生、文档检查、C++ 构建与 CTest、Rust 检查与测试、前端构建与测试。前端目录还没进仓库时，这一阶段会自动跳过。

本地提交前，Git hook 调用同一个脚本的 `--staged` 模式。GitHub Actions 也调用这个脚本，只是分到不同 job 里。这样本地和 CI 不会各有一套检查逻辑。

提交前的检查会根据改动路径触发对应阶段。比如只改 Rust，就不跑 C++。检查范围内如果有未暂存或未跟踪的改动，hook 会直接失败，避免“测的不是要提交的那份代码”。

CI 放在 `.github/workflows/ci.yml`，三个 job 分别做仓库检查与 C++ 构建测试、Rust 测试和前端测试。Actions 固定到具体提交号，权限只给读；同一个分支的新提交会取消旧的运行，省得排队。

交付前还有一道复核：主代理会开一个 reviewer 子代理，按固定清单看 diff，比如有没有重复校验、同一个阈值是不是写了两遍。它只报告问题，不改文件，最后由主代理逐项处理。

### 5.3 仓库卫生与提交

仓库自带 `.githooks/pre-commit`，用 `tools/install-hooks.sh` 一键安装，不需要每个人自己写 hook。

仓库卫生检查做两件事。第一，看 `.gitignore` 和 Git 索引是否一致，避免“明明忽略了却还在跟踪”的情况。第二，看单个跟踪文件是否超过 5 MiB，超过就拦下来，提醒把资产移到仓外。模型、音频、引擎这些大块头本来就不进仓库。

### 5.4 部署与部署后测试：各一条命令

部署用 `tools/deploy-jetson.sh <SSH目标>`。脚本在本机执行，通过 rsync 把源码同步到设备，再通过 SSH 在设备上原生构建。设备地址不写进仓库，由参数或环境变量提供。

部署分五步：部署前快照、源码同步与预检、构建、安装与重启、摘要。默认增量执行，`--full` 强制全量。几个为维护性做的处理：

- 默认按内容同步源码：rsync 用 `--checksum` 判断变更，变更文件落传输时刻的时间戳，cargo/ninja 只重编受影响部分；安装用临时文件加原子替换，不打断运行中的进程，随后只重启二进制变化的服务。
- `--full` 恢复全量路径：前拨全部源码时间戳、重置 Cargo 指纹，强制全量重编并整栈重启。这是为规避旧问题保留的兜底：rsync 保留本机旧时间戳时，构建工具可能误判“源码没变”而跳过重编，最后装上一个落后的二进制。这个坑在实测里暴露过。
- 安装前把上一代二进制备份到 `bin.prev`。安装或重启失败，就恢复上一代并重启旧栈。
- 任一步失败或中断，都会恢复部署前的源码快照。
- 部署成功会写 `deploy.json`，记录提交号、是否有未提交改动、时间、构建预设、部署模式和实际重启的服务。出了问题能查到当时部署的是哪一版、动了哪些服务。

部署本身不跑测试。测试放在部署后，由 `tools/jetson-e2e.sh <SSH目标> [套件]` 负责。套件分单元测试、三进程冒烟、文件转换链路、字幕/翻译/播报链路和性能测量。功能套件开始前会先停运行时，结束后再拉起来，避免和正在运行的服务抢音频设备。

选择在设备上原生构建，而不是交叉编译，主要是为了少维护一套交叉工具链。代价是每次部署都要在设备上编译，增量模式下只编受影响部分。

### 5.5 这套技术栈解决了什么

- 新人不用问“该跑哪条命令”，三条命令覆盖本机测试、部署和部署后测试。
- 本地和 CI 用同一套检查，减少“本地过了、CI 挂了”的情况。
- 构建参数放在预设里，主机和设备各用各的，不靠口头约定。
- 部署失败有回退路径，部署记录可追溯。
- 检查失败会给出文件和行号，修起来有目标。

## 6 对应评分表

| 评分项 | 对应做法 |
| --- | --- |
| 架构设计合理性 | 模块解耦、依赖方向明确、控制面与数据面分开、部署失败可回退、设计决定有变更记录 |
| 功能扩展潜力 | 帧契约稳定、消费者列表和模型注册表配置化、推理层可独立替换 |
| 技术通用价值 | 文档化、二进制夹具可复现、构建预设和实测报告可复现 |
| 系统稳定性 | 进程隔离、daemon 监管与退避重启、实时路径不打日志、能力不足时明确拒绝而不是悄悄降级 |
| 人机协同提效 | 规格给 AI 明确的输入和验收边界；计划模式先确认再动手；交付前由 reviewer 子代理复核 diff；检查脚本给出可验证的失败点 |

评分表里“端云协同”这一条，我们是纯本地方案，没有云端。答辩时可以说明：这样做是为了音频不出设备，代价是模型和算力都受设备限制。

## 7 边界说明

这套维护性有不少是靠约定和流程撑起来的，还没全部变成自动检查。

- 文档长度和“限制句”的检查还没实现，目前只检查行尾空白和报告里的“适用范围”一节。
- 原子发布和主动回滚还没做。现在是固定运行位加 `bin.prev` 备份，失败能恢复，但不能一条命令切回上上个版本。
- 帧契约目前有大小断言，还没有字段偏移断言。
- 模块规格还标着“讨论中”，待办清单里也有没打勾的项。

这些不影响现在的使用，但说明维护性建设还在路上。
