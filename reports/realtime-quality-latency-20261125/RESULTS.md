# 实时变声质量与延迟优化实测报告（Jetson）

- 日期：2026-11-25
- 设备：Jetson Orin Nano Super 8 GB（`MAXN_SUPER`），JetPack 6，TensorRT 10.16
- 基线提交：`20e9700`（已包含 `pre` 20 ms 固定帧长与扩大 ALSA 缓冲两项修复）

---

## 适用范围

- **覆盖场景**：Jetson Orin Nano Super 下的 48 kHz（`bocchi-v2-48k`，含 439 MB 特征索引，3561 个质心、138,915 条向量）与 40 kHz（`tomori-v2-40k`，含 344 MB 特征索引）实时变声推理、ALSA 回环延迟与 60 s 长跑。
- **主测模型默认预设**：`pitch_shift=5`、`index_rate=0.8`、`rms_mix_rate=1.0`、`protect=0.4`、`f0_method=rmvpe`。
- **未覆盖范围**：真实 USB 麦克风实录、32 kHz 主观听感、为其他模型重建 160 ms 引擎。

## 一、背景与测试方法

### 1. 实时变声是怎么工作的

实时链路分成音频进程（`pre`）和推理进程（`rvc`）两部分，按固定节拍运转：

1. `pre` 每 20 ms 采一包音频发给 `rvc`，并按 1:1 节拍取回一包变声结果播放。
2. `rvc` 攒满 240 ms（12 包）后，连同过去 2.5 s 的历史声音一起送入 GPU 推理，产出 300 ms 波形。
3. 新旧两块之间有 60 ms 重叠区。系统先在 10 ms 范围内用 SOLA 对齐波形，再用 50 ms 交叉淡化拼在一起。
4. 流刚启动时，`rvc` 先输出一段静音作为启动缓冲（原默认 400 ms），让后台先算出成品，避免播放断音。

本轮优化瞄准两个问题：一是听感上偶发停顿爆音、断音和字头发闷；二是端到端延迟偏高（基线 582 ms）。

### 2. 怎么测，为什么用两套方法

本轮同时用了两套测试，各司其职：

- **ALSA 回环测试（测真实延迟与长跑）**：用 `aplay` 经 `snd-aloop` 喂给 `pre` 和 `rvc`，再用 `arecord` 录回输出。
  - 脉冲串（8 个 220 Hz 短脉冲）：减去直连回环地板（503.38 ms），得到物理回环净延迟。
  - 30 s 中文男声与 60 s 拼接语料：观察停顿跳变、缺帧、欠载和长跑稳定性。
- **固定起点测试（单独验每步算法）**：复核时发现，ALSA 回环每次启动的时刻不同，音频落在 240 ms 块网格上的位置会随机偏移。同一份代码多跑几次，`Log-Mel L1` 会自然波动 `±0.12 dB`，SOLA 游走会波动 `±5 ms`，足以盖过细微算法差异。因此我们直接向 `mozart-rvc` 喂入 16 kHz 音频，在 0 / 60 / 120 / 180 ms 四个固定起点各跑一次并取均值。每次按块等待算完，做到零欠载、零相位随机性。

## 二、分步改动与逐项复盘

### 模块 A：音质与连续性

#### 步骤 1：静音跳过时淡出尾音，并同步推进音高缓存（`2ac8de0`）

- **做了什么**：
  1. 语音转静音跳过推理时，不再直接丢弃残留的 50 ms 尾音，而是用余弦窗平滑淡出。
  2. 静音跳过期间，向 1024 帧历史音高缓存补入等长零音高，防止停顿后再开口时音高与音频错位。
- **实测结果**：**有真实提升**。固定四起点均值下，停顿边界跳变 P95 从 `0.0080` 降到 `0.0067`（`-16%`），`Log-Mel L1` 从 `7.6958` 降到 `7.6635 dB`，SOLA 标准差从 `3.88` 降到 `3.77 ms`。ALSA 回环的全局最大跳变从 `0.2518` 降到 `0.2057`，且后续全部 20 次运行均低于基线。
- **结论**：**保留**。

#### 步骤 2：放宽时间戳抖动触发的全量重置（`32a0955`）

- **做了什么**：修改 `StreamingRvc::push`，当帧序号 `frame_idx` 连续、没有丢包时，不再因单次送达间隔超过 200 ms 就清空历史并重置流；仅保留缺号、回绕和时间戳倒退重置。
- **实测结果**：**防御有效，稳态指标无变化**。本机 ALSA 回环本身不会出现超 200 ms 间隔，因此 30 s 声学指标与步骤 1 完全一致。C++ 单测已验证连续帧号叠加 `+2 s` 抖动时重置次数保持为 0。
- **结论**：**保留**。

#### 步骤 3：实时改用固定位置生成噪声与连续初相，并加 SOLA 静音门限（`0ce4be2` → `71cb0c1` 回滚）

- **做了什么**：原计划将离线分窗用的「按全局位置生成噪声 + 累计音高初相」引入实时推理，同时给 SOLA 加上 `-50 dBFS`（`3e-3`）弱音门限。
- **实测结果**：**没有提升，反而全项退化**。固定四起点对照显示，合入后 `Log-Mel L1` 变差 `+0.14 dB`（`7.6635 → 7.8028 dB`），`RMS L1` 变差 `+0.14 dB`，SOLA 游走从 `10.94` 恶化到 `12.33 ms`，停顿跳变和接缝指标同步变差。进一步拆开消融查明原因：
  1. **连续初相有害**：RVC v2 解码器训练时基波初相恒为 0，且累计周期未耦合 SOLA 偏移。强行传入非零初相后，单独一项就让 SOLA 游走飙升到 `13.61 ms`。
  2. **实时计算噪声偏慢且略退**：每块计算 2.4 万次哈希与三角函数，多花约 `4.9 ms` CPU 时间，即使关闭初相仍带来 `+0.08 dB` 频谱退化。
  3. **SOLA 门限误伤弱音**：`3e-3` 门限拦掉了可听轻辅音与字尾对齐，带来 `+0.08 dB` 退化；降到 `1e-3` 也无净收益。
- **结论**：**已完整回滚（`71cb0c1`）**。

#### 步骤 4：实时补齐清辅音保护、音量跟随与峰值限幅（`2f58b3c` + `71cb0c1` 修正）

- **做了什么**：在 `infer_realtime` 中补齐离线链路已有、实时缺失的三步：按 `protect` 保护无基频的清辅音帧；按 `rms_mix_rate` 用 120 ms 窗做音量跟随（弱输入 `< 0.005` 不放大）；输出统一做 `0.99` 峰值限幅。
- **实测结果**：**有效，但前期存在漏测，已补测并修正**。
  - 前期误判说明：`bocchi-v2-48k` 预设写死了 `rms_mix_rate = 1.0`，导致前 21 次 ALSA 回环里音量跟随分支从未执行。
  - 清辅音保护（`r=1.0`）：在回滚步骤 3 后，四起点对比显示 `protect = 0.4` 相比基线与步骤 1，停顿跳变（`0.0096 / 0.0065`）、`Log-Mel L1`（`7.6615 dB`）、`RMS L1`（`4.1707 dB`）和 SOLA 游走（`10.70 ms`）全项继续小幅改善。
  - 音量跟随（补测 `rms_mix = 0.5 / 0.25`）：初版在块首尾计算 RMS 时仍除以完整 120 ms 窗长，造成块边缘增益衰减。修正为除以实际有效样本数后，`rms_mix = 0.5` 将输出与原声的音量相关性从 `0.686` 提到 `0.820`，动态误差从 `5.68` 降到 `4.69 dB`，静音底噪从 `0.0071` 降至 `0.0036`，SOLA 游走保持在 `10.79 ms`。
- **结论**：**修正后保留**。

### 模块 B：速度与延迟

#### 优化 5：重写特征索引搜索（`e5f29d8`）

- **做了什么**：定位到带大索引的模型（3561 个质心）单块耗时里，有 `88.6 ms` 消耗在 CPU 单线程逐个计算上，且每帧都在重复读取 10.9 MB 质心表。改写 `IndexSearch::search()`：用 AArch64 NEON 一次算 16 个浮点，按 32 帧分块让质心只读一次主存，并拆给 4 个线程并行。
- **实测结果**：**大幅提升，零音质代价**。索引检索从 `88.6 ms` 降到 `6.0 ms`（快 14.8 倍）。老 FP32 模型整块推理从 `176.7 ms` 降到 `100.0 ms`，FP16 模型从 `142.7 ms` 降到 `56.0 ms`。单测验证与原标量算法最大误差 `< 1e-4`，同相位下声学输出一致。
- **结论**：**保留**。

#### 优化 6：启动缓冲下界验证与默认值调整（`e99a033`）

- **做了什么**：实测扫描 `startup_delay_ms`，验证最小安全缓冲满足公式：

  $$D_{\min} = W + T_{\text{infer,max}}$$

  其中 $W$ 是块长（240 ms），$T_{\text{infer,max}}$ 是单块最大推理耗时。
- **实测结果**：
  - 优化前（FP32 推理 `177~206 ms`）：$D_{\min} \approx 420\text{–}440\text{ ms}$。把启动缓冲硬调到 `320 / 280 / 240 / 200 ms` 时，净延迟仍卡在 `582 ms` 一点没降，缺帧数从 1 暴涨到 10（每次缺帧补 20 ms 静音会把延迟推回原位）。
  - 索引加速后（老 FP32 推理降至 `100 ms`）：$D_{\min} \approx 340\text{ ms}$。`startup_delay_ms = 340` 在 48 kHz 与 40 kHz 两套老 FP32 模型上均达成零缺帧，净延迟直接降到 `481.8 / 478.8 ms`（省约 `101 ms`）。
- **结论**：**保留，已将默认 `startup_delay_ms` 从 400 降为 340**（兼顾既有 FP32 资产零缺帧）。

#### 优化 7：本机 FP16 重编实时引擎（`e99a033`）

- **做了什么**：在 Jetson 本机用 `build_realtime_engines.py --fp16` 重编四套实时引擎（`front`、`decoder`、`hubert`、`rmvpe`），消除跨设备引擎警告，并将配置默认改为 `compile.fp16 = true`。
- **实测结果**：**延迟大降、音质近无损**。
  - `trtexec` 单引擎纯 GPU 耗时降至 `front 5.5 ms`、`decoder 6.5 ms`、`hubert 10.1 ms`、`rmvpe 5.3 ms`。
  - 搭配索引加速与回滚步骤 3 后，实测整块推理降至 **`56.0 ms`**（P95 `60.7 ms`，比基线快 3.15 倍）。
  - 启动缓冲可进一步压到 `320 ms`（净延迟 `459.3 ms`）乃至 **`300 ms`（净延迟 `435.3 ms`，比基线省 `147.2 ms`）**，均零缺帧、零欠载，ALSA 回环 `Log-Mel L1` 达 `4.687 dB`。
- **结论**：**保留**。

#### 优化 8：160 ms 短块实验（隔离实测，未合入默认）

- **做了什么**：将块长从 240 ms（3840 样本）缩到 160 ms（2560 样本），重新导出并编译 FP16 引擎（`front=272`、`decoder=22`、`hubert=43520`、`rmvpe=32`），在隔离目录实测延迟、质量与 60 s 长跑。
- **实测结果**：**延迟降到极值，但音质有轻微代价且不兼容旧模型**。
  - 单块推理 `51.3~52.4 ms`（GPU 占空比 32.8%）。`startup_delay_ms = 240 / 220` 均通过 60 s 零缺帧长跑（378 块，零欠载），净延迟压到 **`385.6 / 365.6 ms`**（比基线省 `197 / 217 ms`，纯 RVC 相对直出仅滞后 `266 ms`）。
  - 代价：3 次实测 `Log-Mel L1` 均在 `4.97~4.99 dB`、`RMS L1` 在 `2.76~2.91 dB`，系统性略弱于 240 ms（`4.69~4.86 dB`），每秒接缝数从 4.17 次增至 6.25 次；且修改块长会让现有的 240 ms 模型失效。
- **结论**：**暂不切换主干默认块长**，保留完整数据供后续支持多几何自动适配后按需启用。

## 四、本轮排查出的后续优化方向

在对比直驱、回环与硬件状态时，发现四处尚未动过、但收益明确的剩余空间：

1. **Jetson GPU 空闲降频（预计再省 `~19 ms` 推理 / `~20 ms` 延迟）**：板端实测显示，`nvhost_podgov` 在每两块 240 ms 的间隙会把 GPU 从 `1020 MHz` 降到 `306 MHz`。这直接导致连续直驱只要 `37.2 ms`，真实节拍下拖慢到 `56.0 ms`。锁定 GPU 频率即可消除这部分升频损耗。
2. **`TrtEngine` 拷贝阻塞双流并行（预计再省 `5~10 ms` 推理）**：`TrtEngine` 用普通 `std::vector` 做异步拷贝，触发了 CUDA 隐式同步。分段耗时显示 RMVPE 的入队干等了 `27 ms`，实际在排队等 HuBERT 跑完。改用锁页内存可让两者真正并行。
3. **`pre` 采播管道占约 `100 ms`（预计可压 `30~50 ms`）**：目前采集和播放缓冲各设了 `2176` 样本（`45.3 ms`），播放起播阈值 `40 ms`。在 `rvc` 推理稳定在 `56 ms` 以内后，可重新收紧采集缓冲与起播水位，不改任何模型即可再降延迟。
4. **音质细节与多档位兼容**：`pre` 对 40k/32k 模型输出目前采用逐样本线性插值升采样到 48 kHz，高频混叠较重（`tomori-v2-40k` 跳变明显高于 48 kHz 模型）。此外，还可补上实时 F0 轻度中值滤波、`protect`/`rms_mix_rate` 在线热更，并支持从引擎输入尺寸自动推导块长，让 240 ms 与 160 ms 模型并存。
